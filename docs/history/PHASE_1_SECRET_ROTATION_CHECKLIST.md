# Phase 1 Secret Rotation Checklist

## Handling Rules

No real secret values are included here. Do not paste them into this checklist, source files, test fixtures, terminal output, logs, or reports. Inject values from an approved secret manager or secure runtime environment. No credential below is claimed as rotated by this repository change.

| Credential | Purpose and expected runtime location | Rotation action | Session/token invalidation | Verification | Rollback consideration |
|---|---|---|---|---|---|
| JWT signing secret | Signs dashboard/platform-admin JWTs; injected as `JWT_SECRET` independently per environment. | Generate a new high-entropy value (48+ bytes), store in the environment secret manager, deploy to the backend. | The new signing key invalidates all old JWTs; users and platform admins must log in again. Check for any other service sharing the old key and rotate it there too. | Verify missing/weak startup config is rejected; verify a token signed by the old key returns 401 and a new login token works. | Do not restore the old key after exposure. If rollout fails, use a separately generated replacement and reissue sessions; preserve availability via deployment rollback only if the old key was never compromised. |
| MongoDB credentials / URI | Backend DB access; injected as `MONGODB_URI` from the database secret manager. | Create a least-privilege replacement service identity scoped to each environment/database, update secret injection, then revoke old credentials. | Not a JWT session; review exposed DB sessions/credentials and terminate old DB connections after deployment. | Connect using the new principal; confirm allowed application operations work and unauthorized databases/operations fail. | Keep old credential disabled, not reactivated, if exposure is confirmed. Restore from a verified backup if data/schema migration must roll back. |
| SMTP credentials | Outbound alert delivery; `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, and `SMTP_FROM` runtime configuration. | Rotate the SMTP account/password with the mail provider; apply provider restrictions and update the secret manager. | Revoke old provider sessions/tokens; no dashboard JWT invalidation is required unless credentials were reused. | Send a controlled staging email and confirm no secret appears in logs or response payloads. | Keep a second restricted provider credential ready during planned rotation; revoke any value suspected exposed. |
| Slack webhook credentials | Tenant alert delivery stored in tenant org configuration; webhook secret originates from Slack and must be treated as a credential. | Revoke/regenerate the webhook at Slack; update only the owning tenant configuration through the approved admin workflow. | No JWT invalidation needed; remove stale webhook values from org settings after provider revocation. | Send a controlled test alert to the intended channel; verify the old webhook no longer accepts posts. | Keep the old webhook revoked if compromised; do not restore it for rollback. |
| Previously exposed account password | A literal account password was previously present in `backend/reset-password.mjs`; the reset tool now requires runtime `RESET_PASSWORD` and scoped email/org inputs. | Treat the exposed password as compromised; reset the affected account to a new unique password through the identity owner, without recording it here. | Increment the affected user's auth version, revoke active sessions/WebSockets, and invalidate any reused passwords at other services. | Confirm old password fails, new password succeeds, old JWT fails, and no plaintext value appears in source/history/logs. | Do not restore the exposed password. Recover through the authorized password reset process. |
| Platform-admin bootstrap password | Bootstraps the separate platform-admin principal; supplied as `PLATFORM_ADMIN_PASSWORD` to `npm run provision:platform-admin`, then retained only as an adaptive password hash in MongoDB. | Use a unique high-entropy value delivered through a one-time secure channel; rotate via an approved admin maintenance process if exposed. | Increment the platform admin auth version and invalidate existing platform-admin tokens after rotation. | Verify platform-admin login with the new password; tenant credentials must not authenticate on platform-admin routes. | Do not re-enable a compromised password; bootstrap a replacement platform admin only through controlled operator access. |
| Device credentials and pairing codes | Per-device opaque token stored hashed in MongoDB and in extension `chrome.storage.local`; one-time pairing code is hashed server-side and expires after five minutes. | Revoke the affected device, remove its extension-local credential, and perform a new user-authorized enrollment. | Device tokens are checked against active database state on every request; revocation immediately rejects the credential. Expired/used pairing codes cannot be redeemed again. | Confirm revoked credential gets 401, replacement device can submit an authenticated event, and raw token/code is absent from DB/logs. | Never reactivate a suspected compromised device token; issue a new device identity. |
| Extension API origin | Not a secret; build configuration in `VITE_API_URL`, with `.env.development`, `.env.staging`, or `.env.production` local files excluded from source control. | Update the environment-specific origin and rebuild. Staging/production must use non-local HTTPS origins. | Rebuild/redeploy the extension; existing device credentials are independent but may need endpoint migration/re-enrollment. | Inspect packaged `dist/manifest.json` host permissions and generated background bundle; production config rejects HTTP/localhost. | Roll back to a previous signed build only if its API origin remains approved and secure. Never use localhost HTTP as a production fallback. |
| Other repository/history/runtime credentials | May include connection strings, alert targets, webhook values, CI/deployment secrets, or credentials retained in Git history; values have not been inspected or printed. | Security/operations owner runs an approved secret scanner/history review, inventories owners, rotates every live credential found, and follows repository governance for history sanitation. | Revoke provider sessions/tokens and affected user/device credentials as appropriate. | Re-scan current tree and history using approved tooling; independently confirm provider-side old credentials fail. | Preserve an incident record and verified data backups; do not reintroduce a credential to recover deployment availability. |
